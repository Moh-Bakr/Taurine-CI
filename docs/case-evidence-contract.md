# Case evidence contract

Status: **activated in the Linux browser concerns; producer honesty and runner completeness remain unverified.** The validator now runs inside the protected concern job and a reconciliation failure fails that concern. It still does not enable test selection and does not qualify a partial run for admission: the full validation baseline remains authoritative, and the validator's clean status is still `shadow_valid_unverified_producer`.

## Activation (owner decision, 2026-10-14)

`.github/policy/case-evidence-admission.rb` is the trusted producer for the admission path, invoked by the "Reconcile case evidence for the browser concern" step of `linux-validation-concern.yml` after the source token is revoked and root is dropped. The step is written out in that workflow rather than in a composite action: a new local action is only reviewable across two merges, because the base commit's `check-actions.sh` allow-list runs against a pull request's tree.

It adds only the discovery half. The reviewed browser concern already writes a Playwright JSON execution report to `RUNNER_TEMP/test-ids/<concern>.json`; the producer runs one `playwright test --list --project <project>` per project with the control-owned reporter — no browser, no web server, no second execution of the suite — and hands both halves to the unchanged validator, once per project.

Reconciled concerns and their scopes:

| Concern | Tier | Projects |
| --- | --- | --- |
| `e2e-critical` | `feedback` | `smoke`, `critical`, `shell-browser` |
| `e2e-a11y` | `a11y` | `a11y` |
| `e2e-visual` | `visual` | `visual` |

Because `e2e-critical` runs three projects in one command while the validator binds one project per envelope, the producer partitions the execution report by `projectName` in control code and validates each partition separately. Before partitioning it asserts that every executed case belongs to one of that concern's reviewed projects, so a case no project owns blocks instead of being silently dropped; afterwards it asserts the partitions account for every executed case and, where the runner supplied `stats`, that those totals equal the reconciled total.

The four `e2e-regression-*` concerns are **not** reconciled. 1.62.0 does apply `--shard` to `--list`, so a shard job could compare its own quarter against its own listing — but that is a weaker claim than this gate makes elsewhere: a single shard job cannot show that the four shards together ran the whole project, and nothing in a shard job can see the other three. Reconciling them would mean the same green badge standing for two different claims, so the producer refuses those concerns instead.

Nothing is relaxed by this activation: no coverage floor, suite floor or required concern changed, no selector was enabled, and the result is an additional fail-closed step on an already-mandatory concern.

The producer verifies the identities it runs under rather than trusting the step that passed them in: the source and control checkouts must be at the expected commits, the source checkout must be clean, `.github/ci-matrix.json` and the source's ownership manifest, lockfile and `playwright.config.ts` must match their commits byte for byte, the recomputed catalog and manifest digests must match, the selected suite IDs must be exactly one reviewed coverage group's candidate set, and the installed runner must be the reviewed 1.62.0 pin with its integrity hashes. A lockfile bump therefore blocks as `runner_version_unpinned` rather than running this gate against a report shape nothing has proven. The ownership manifest is source-owned, so its absence blocks as `manifest_absent` instead of skipping the step.

## What the validator checks

`.github/policy/case-evidence-contract.rb` accepts a control-generated expected-identity file plus one discovery envelope and one execution envelope. It checks exact envelope keys and schema version, fixed adapter/command identifiers, producer version and status, locked tool-version equality, 40-hex source/control commit identities, manifest/catalog/selection SHA-256 identities, and the JSON report digest. Both reports must use the same runner, config, tier, platform, and expected identity values. The selected-suite list must match the expected set, and its SHA-256 digest is computed from the sorted JSON list.

For each report, the validator derives private case IDs from the same identity fields used by the private audit: runner, config, tier, platform, project, normalized file path, binary ID, package, and title. Vitest and Playwright do not populate binary/package fields, so those identity slots are empty. For Playwright's execution JSON, every suite node carries a file path; the validator skips the top-level file-suite title and retains nested describe-suite titles to match the discovery reporter's full title chain. IDs are used only inside this process to reject duplicates and compare discovery with execution. The validator then returns aggregate counts and a fixed status or error code. It never emits report paths, titles, raw reports, case IDs, or case-ID hashes.

`collection_complete: true` and `producer_status: complete` are producer claims, not proof. The contract also requires nonempty structured reports, parser-valid entries and statuses, exact reporter counts where available, exact execution/discovery ID agreement, and exact agreement with the execution envelope's discovered-ID set. For Playwright, the test-level aggregate status controls the outcome; retry result statuses are validated but cannot override an aggregate `unexpected`, `flaky`, or `skipped` status. The optional `expectedStatus` may be `passed`, `failed`, `timedOut`, `skipped`, or `interrupted`; when omitted it defaults to `passed`. An aggregate expected outcome is accepted only when every attempt matches that expectation, which supports intentional expected failures without treating a mismatched expectation as passing. If the execution report includes `stats`, all four outcome counters (`expected`, `skipped`, `unexpected`, and `flaky`) must be nonnegative integers and reconcile with the parsed outcomes. Reporter errors or malformed error records block the report. A structurally consistent producer can still lie about having invoked the named command; therefore a clean result is `shadow_valid_unverified_producer`, never an admission pass.

Both structural errors and valid-but-nonpassing outcomes return a sanitized `shadow_blocked` JSON object and exit nonzero. Only a structurally reconciled all-passing result exits zero, and it remains unverified shadow evidence.

## Version 1 envelope shape

The envelope retains the private audit's field names: `schema_version`, `phase`, `source_sha`, `control_sha`, `manifest_digest`, `catalog_digest`, `selection_digest`, `collection_complete`, `collection_digest`, `runner_id`, `config_id`, `tier`, `platform`, and `report`. Version 1 adds `producer_version`, `command_id`, `tool_version`, and `producer_status` so a future trusted caller can bind the exact adapter and executable version. An execution envelope also carries `selected_suite_ids` and `discovered_case_ids`, matching the existing private audit contract. The `collection_digest` is SHA-256 over the structured report's JSON serialization, as in the existing private normalizer.

The expected-identity file is generated by trusted control-plane code before project tests run. Its exact fields are `schema_version`, `source_sha`, `control_sha`, `manifest_digest`, `catalog_digest`, `selection_digest`, `selection_mode`, `selected_suite_ids`, `runner_id`, `config_id`, `tier`, `platform`, `project`, `tool_version`, and `repo_root`. It is never read from the source repository. The standalone validator checks that the selection digest matches the sorted selected-suite IDs; a future workflow must independently derive the expected IDs and digests from its protected catalog and source checkout.

## Fixed adapter registry for a future producer

Command identifiers map to fixed arguments in trusted control code. No executable, argument, environment override, test title, or filter expression is accepted from an evidence envelope or source manifest. Resolve runner binaries only inside the checked-out package named by the adapter, validate the resolved path remains inside that package, and pass an argv array with `shell: false`.

| Adapter | Discovery invocation proposal | Execution invocation proposal |
| --- | --- | --- |
| `vitest-desktop` / `desktop-vitest-default` | From `taurine-desktop`: resolved Vitest binary, `list --config vitest.config.ts --json` | Same binary, `run --config vitest.config.ts --reporter=json --outputFile=$RUNNER_TEMP/case-evidence/vitest-desktop.json --includeTaskLocation` |
| `vitest-mobile` / `mobile-vitest-default` | From `taurine-mobile`: resolved Vitest binary, `list --config vitest.config.ts --json` | Same binary, `run --config vitest.config.ts --reporter=json --outputFile=$RUNNER_TEMP/case-evidence/vitest-mobile.json --includeTaskLocation` |
| `vitest-shared` / `shared-vitest-default` | From repository root: resolved Vitest binary, `list --config vitest.packages.config.ts --json` | Same binary, `run --config vitest.packages.config.ts --reporter=json --outputFile=$RUNNER_TEMP/case-evidence/vitest-shared.json --includeTaskLocation` |
| `playwright-desktop` / `desktop-playwright-projects` | From `taurine-desktop`: resolved Playwright binary, `test --config playwright.config.ts --list --project=<one allowlisted project> --reporter=<control-owned case-list reporter>` | Same binary, `test --config playwright.config.ts --project=<one allowlisted project> --reporter=json`; fixed `PLAYWRIGHT_JSON_OUTPUT_NAME` points into `RUNNER_TEMP` |
| `playwright-mobile` / `mobile-playwright-projects` | From `taurine-mobile`: resolved Playwright binary, `test --config playwright.config.ts --list --project=<one allowlisted project> --reporter=<control-owned case-list reporter>` | Same binary and fixed JSON output contract as desktop |

Vitest's three config files are the private manifest's existing desktop, mobile, and shared configurations. The private audit already parses a Vitest list array (`file`, `name`, optional `projectName`) and JSON execution assertions. Before using those IDs for any selector, a pinned Vitest fixture must prove that list names normalize exactly to execution `ancestorTitles + title` across parameterized tests, duplicate names, and projects. The current private runner explicitly avoids per-case filtering until this equivalence is proven.

Playwright uses one fixed invocation per project. Desktop project allowlists are: feedback (`smoke`, `critical`, `shell-browser`), regression (`regression`), benchmark (`bench`), accessibility (`a11y`), and visual (`visual`). Mobile allowlists are `smoke`, `critical`, and `regression`. The public collector currently supports desktop Playwright only; adding mobile Playwright is a separate coverage change. A control-owned list reporter and its exact machine-readable output are not implemented or verified here. The command form above is a proposal, not evidence that the pinned Playwright version supports it.

For every adapter, the producer must capture the exact locked runner version from the source lockfile, execute only the fixed command ID for that phase, verify successful process exit and complete structured output, and derive IDs/status/counts from the parsed report. For execution, the trusted audit re-parses the report and requires exact equality between discovery IDs, execution IDs, and `discovered_case_ids`; additions, omissions, duplicates, malformed records, empty required reports, or non-passing statuses cannot be converted into a clean result. Raw reports and IDs stay in an ephemeral `RUNNER_TEMP` directory with restrictive permissions and are not uploaded as artifacts.

## What activation does and does not establish

It establishes, on every reconciled concern: that the pinned runner's discovery and its execution agree case for case, that no executed case lacks a discovered identity and no discovered case went unexecuted, that no two cases share an identity, that no suite came back unexpectedly empty, and that every executed case belongs to a reviewed project of that concern.

It does not establish that the producer is honest about having invoked the command it names; that the four sharded regression concerns are case-complete; that the mobile Playwright adapter works at all (no mobile concern is reconciled); or anything whatsoever about Vitest, whose list/run parity is still unproven and whose adapters below remain proposals.

It is also not *discovery completeness* in the broad sense, and the phrase is avoided deliberately. Reconciliation is per-project self-consistency under the source project's own `playwright.config.ts`: its `testDir`, its `grep` and its `grepInvert` decide which cases exist for a project, and both halves of the comparison inherit those decisions. Three consequences, each reproduced against the pinned runner and none of them new in this change:

- a case tagged for two tiers runs twice, once per project, and both runs reconcile, so duplicate execution across projects is not detected here;
- a case retagged out of every gated tier (for example to `@slow`, which only the ungated `bench` project greps) disappears from both halves and reconciles;
- there is no floor on the number of cases, so a config change that empties a project fails only if it empties it entirely, which blocks as `case_collection_empty`.

What the gate does catch is a disagreement between what the pinned runner says it will run and what it reports having run, for the projects a concern is bound to.

## Outcomes that are reported rather than blocked

A case that passed on a retry its project's config permits, and a case the suite deliberately skips, are not parity failures: the runner reported both and exited zero. Blocking on them would silently override the source project's one-retry policy and its deliberate skips, which is a product decision and not this gate's to take. They are counted as `retried_pass` and `skipped` in the sanitized summary, never folded into `passed`, so a reader can see them. The blocking scope is exactly: a discovered case that was not executed, an executed case that was not discovered, a duplicate case identity, an empty suite, a case belonging to no reviewed project of that concern, a missing ownership manifest, a runner version that is not the reviewed pin, and any identity that does not match git. Each blocks under its own error class.

## Gaps and admission boundary

The current public collector keeps file/status/project counts and discards per-case titles; its public manifest contains file globs rather than expected case IDs. The private exact-case parser and audit exist in the ADE source snapshot but are not invoked by the current public workflows. The private publisher that writes case titles to Markdown is not a completeness source and is not used here.

This stage implements only a structural contract and synthetic fixtures. Nextest, doctest, normalized, and native-platform evidence are not supported by this validator. The report itself cannot prove that its producer invoked the registered binary or enumerated every case. A future protected producer must bind the command to trusted control code and the exact source/control/manifest/catalog/selection identities, and must establish runner-specific list/run parity with pinned fixtures and hosted evidence. Until those gates exist, case evidence remains shadow-only and the full concern matrix stays mandatory.

## Trust-boundary fixture and producer gates

`.github/policy/test-case-evidence-trust-boundary.sh` creates synthetic JSON without invoking Playwright, Vitest, or either producer. It deliberately forges `producer_status: complete`, `collection_complete: true`, matching report digests, and matching discovery/execution identities; the only clean result remains `shadow_valid_unverified_producer`. A second fixture recomputes the execution digest and submitted ID list after adding an execution-only case; the independent discovery comparison blocks it. These fixtures test the validator's structural boundary, not producer honesty, runner completeness, or hosted execution.

In the inspected private Taurine source checkout, desktop locks `@playwright/test` 1.62.0, mobile locks 1.62.1, and both app locks pin Vitest 4.1.11; that source checkout's root package lock pins Playwright 1.63.0. The shared Vitest adapter resolves the desktop package's local Vitest binary while using `vitest.packages.config.ts`. A producer must bind its runtime version to the relevant app lock, not infer it from the private source root. Any custom Playwright reporter or Vitest list/run normalization needs parity fixtures against these exact package versions before the producer can be considered trustworthy.

A future producer should live only in protected control code and own a fixed command registry, argv arrays, app-local binary resolution, and output parsing. It should write raw reports and private case IDs to a restrictive temporary directory owned by the job, fail on command error, malformed/empty reports, count or identity disagreement, and publish only fixed aggregate counts plus the validator's shadow status. The evidence consumer should receive files from that control-owned directory, not paths or command choices supplied by the source checkout. Expected catalog, manifest, source, control, config, platform, project, and selection identities must be independently derived before invocation. No producer boolean or recomputed digest can substitute for these controls.

The runner's shared UID can still modify files in a job-owned temporary directory if untrusted test code executes in the same process/container boundary. Restrictive permissions reduce accidental disclosure but do not establish isolation from code running as that UID. A trusted producer therefore needs an explicit threat-model decision and hosted validation of the chosen process/container boundary; until then, its evidence remains unverified shadow data. This document and the synthetic fixtures do not implement or authorize producer activation, workflow changes, selectors, or admission behavior.

## Fixed Playwright shadow producer prototype

`.github/policy/playwright-case-evidence-producer.rb` and `.github/policy/playwright-case-list-reporter.cjs` implement a local shadow-only prototype. The wrapper accepts exactly one control-generated expected-identity file. It selects desktop or mobile from the fixed runner/config pair and derives the project and tier from the validated allowlist; it accepts no caller-supplied executable, project override, filter, shell fragment, or extra argument. The wrapper binds source and control SHAs to their checked-out Git heads, requires a clean source checkout and the source lockfile, Playwright config, and ownership manifest to match the source commit, recomputes the control catalog and source manifest digests, and requires the selected IDs to equal the full candidate set for exactly one matching runner/config/tier/platform/project scope. It validates each selected suite's project/platform mapping, exact pinned integrity/version entries for `@playwright/test`, `playwright`, and `playwright-core`, and resolves the installed CLI under the selected app's `node_modules`. The expected lock bindings are desktop 1.62.0 and mobile 1.62.1. It invokes a resolved Node executable with an argv array and no shell.

Discovery runs one fixed `playwright test --list --project <allowlisted-project>` command with the control-owned reporter path. The reporter derives a structured suite report from the runner's `onBegin` suite, writes only into the wrapper's private directory, and requires a completion marker with a matching case count. Each callback catches its own errors because Playwright swallows custom reporter callback exceptions; absent, malformed, or failed completion markers block the result. Execution uses the same app-local CLI, fixed config/project, and JSON reporter. The parent independently requires both command exit codes, bounded output, nonempty bounded reports, private regular files, the locked tool version, and exact discovery/execution identity reconciliation through the structural validator.

The child environment is replaced with a small allowlist containing only the resolved executable search path, a fresh temporary home and temp directory, `CI`, report paths needed by the two report phases, and the optional `PLAYWRIGHT_BROWSERS_PATH` when it resolves to an external `ms-playwright` cache directory. It does not inherit arbitrary caller variables or credential variables. Raw reports, titles, file paths, and case IDs remain in a mode-0700 temporary directory with mode-0600 files that is removed when the wrapper exits. Before emitting a validator result, the wrapper checks its exact key set, fixed error class, nonnegative bounded counts, count reconciliation, and exit status, then rebuilds the public JSON from the approved fields. Process output is capped; one deadline covers both child execution and output-pipe draining, and timeout, overflow, or cancellation terminates the child process group before temporary data is removed. The prototype supports Linux and macOS only. It is not wired into any workflow and has not been run against the real locked Playwright installations.

`.github/policy/test-playwright-case-evidence-producer.sh` uses a synthetic source Git repository and a fake Node executable to exercise the wrapper's exact argv, environment scrubbing, lock/config binding, private file permissions, completion-marker failure, runner-version mismatch, extra-case mismatch, validator-output whitelisting, and a child that exits while a descendant retains its output pipes. The fake executable writes synthetic reports; the fixture does not execute the JavaScript reporter, Playwright, browser binaries, or source tests. Passing this fixture is not Playwright parity proof. The shared runner UID can still alter same-UID temporary data, and exact 1.62.0/1.62.1 report-shape and list/run parity still require protected hosted verification. These outputs remain `shadow_valid_unverified_producer`; no selector, workflow, or admission consumer is enabled. Vitest remains unsupported for exact per-case evidence until its pinned list/run parity is proven.
